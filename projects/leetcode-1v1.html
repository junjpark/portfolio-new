Overview

LeetCode 1v1 turns coding practice into a head-to-head race. Join a queue, get matched with a player near your rating, and both of you get the same problem. The first to pass every test case wins.

We built it as the final project for CSE 4207 in Fall 2025, as a set of microservices that talk through events.

What I built

  • Seven services on Kubernetes. The app is a React front end, a Node and Socket.IO API, a TypeScript game server, a Go matchmaker and a judge service, plus Kafka and Redis, each running on Kubernetes.
  • Matchmaking in Go. Each difficulty and match length has its own queue, kept sorted by ELO in a B-tree. Every second, the matchmaker pairs neighboring players who are within 100 rating points.
  • Event streaming. Kafka carries match requests and found matches between the API and the matchmaker. When a match is found, the API picks a problem of the right difficulty and starts the game for both players.
  • Judging. Each submission runs test case by test case in Judge0, and both players see each other's progress live. The editor is Monaco, with seven languages and starter code.

Outcome

  • 7services on Kubernetes
  • ±100ELO matching window
  • 7languages in the editor

LeetCode 1v1 was a learning project first. I wanted hands-on experience with the tools behind large distributed systems: Kubernetes, Kafka, services written in different languages, and the connections between them.

Building it also showed me the cost. Every hop between services adds network latency, serialization and one more thing that can fail, so for an app this size a single monolith would likely be faster and simpler to run. The next step is to test that properly: build a monolith version, benchmark it against the distributed one, and ship whichever performs better.
